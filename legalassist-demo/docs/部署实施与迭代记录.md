## 一、端到端部署流程

实际按 **6 个阶段**推进。每个阶段都有**可验证的产出**，不通过就不进入下一阶段。

```
阶段0 环境探测 → 阶段1 依赖与模型 → 阶段2 语料构建
    → 阶段3 索引构建与预热 → 阶段4 服务启动 → 阶段5 三层验证
```

### 阶段 0 · 环境探测

不假设环境，先探测再动手。这一步避免后面所有时间白费。

| 探测项 | 结果 | 处置 |
|---|---|---|
| Python 解释器 | `python` / `python3` 是 Microsoft Store 占位程序；`py` 指向损坏的 3.13 | 定位到 `%LOCALAPPDATA%\Programs\Python\Python312\python.exe`，全程用绝对路径 |
| 进程 / 端口工具 | Git Bash 里 `pkill` / `netstat` / `taskkill` 均不存在 | 改用 PowerShell `Get-NetTCPConnection` + 定向 `Stop-Process` |
| 终端编码 | 中文 Windows，PowerShell 输出走 GBK，中文会变乱码 | 关键判定改用 ASCII 输出（`FREE` / `LISTENING`），避免误读 |
| `curl` 中文 | Git Bash 的 `curl` 会把中文请求体转成 GBK，服务端收到乱码 | 中文 API 测试一律改用 Python `urllib` 客户端 |

> **安全原则：只按 PID 定向杀进程。**
> `taskkill /F /IM python.exe` 这类按镜像名过滤会误杀用户的其他 Python 任务
> （Jupyter、其他会话），既危险、也应被权限层拦截。

### 阶段 1 · 依赖与模型准备

| 步骤 | 命令 | 产出 |
|---|---|---|
| 装推理依赖 | `pip install onnxruntime tokenizers` | 约 115MB |
| 下载嵌入模型 | `python tools/fetch_model.py` | BGE-small-zh-v1.5 ONNX，512 维，91MB |

下载器 `tools/fetch_model.py` 做了三件事保证可重复：

1. **HF → hf-mirror 双镜像自动切换**（国内网络可用）
2. **断点续传**（大文件失败不用从头再来）
3. **写 `SOURCE.json`** 记录模型来源与下载时间

**模型落地后立刻做语义能力抽检**，确认不是"装了个寂寞"：

| 查询 | 文档 | 余弦 |
|---|---|---|
| 公司没跟我签劳动合同 | 用人单位未与劳动者订立书面劳动合同 | **0.714** |
| 老板不给交社保 | 用人单位未依法缴纳社会保险费 | **0.633** |
| 老公出轨了我能要赔偿吗 | 无过错方有权请求离婚损害赔偿 | **0.622** |
| 对方收了钱就跑路了 | 收取价款后未履行交付义务 | **0.523** |
| 今天天气不错 | 用人单位未依法缴纳社会保险费 | **0.217** |

相关对落在 0.52~0.71，无关 0.22 —— **区分度清晰，才继续往下做**。
如果抽检发现全是 0.4~0.5 挤在一起，说明模型或池化方式有问题，此时应当停下排查，
而不是继续在上面盖楼。

### 阶段 2 · 语料构建

`tools/build_corpus.py` 从两个公开法律仓库拉取并解析成**条级**结构。
关键点：**两个仓库的 Markdown 体例不同**，必须用两套解析器。

| 仓库 | 体例示例 | 覆盖法律 |
|---|---|---|
| `risshun/Chinese_Laws` | `**第一千零七十九条**正文` | 民法典 / 劳动法 / 劳动合同法 |
| `LawRefBook/Laws` | `第一千零七十九条 正文` | 工伤保险条例 / 劳动争议调解仲裁法 / 民间借贷司法解释 |

**规模：32 条 → 1037 条。**

并且做了**真实性校验**——解析出的条数必须与官方公布条数吻合，否则说明解析器有 bug：

| 法律 | 解析条数 | 官方条数 | |
|---|---|---|---|
| 民法典（全） | 1260 | 1260 | ✅ |
| 劳动合同法 | 98 | 98 | ✅ |
| 劳动法 | 107 | 107 | ✅ |
| 工伤保险条例 | 67 | 67 | ✅ |
| 劳动争议调解仲裁法 | 54 | 54 | ✅ |
| 民间借贷司法解释 | 31 | 31 | ✅ |

同时给每条补上**时效元数据**：

- `status`：现行有效 / 已修改 / 已废止
- `effective_date`：施行日期

供风险提示环节判断引用到的法条是否仍然适用。

> **踩坑记录**：中文数字解析起初漏了「二」「〇」「两」等写法；
> 条目循环又有重复 append 导致数量翻倍。
> 这两个 bug 都是靠上面这张校验表发现的——
> **没有校验表，这类错误会静默污染整个知识库**，而且很难在使用中察觉。

### 阶段 3 · 索引构建与预热

`app/engine/vector_index.py` 承担三件事：

**① 批量编码 —— 按长度分桶**

法条长短悬殊（13~392 字）。若一次性 padding 到最长条目，
实际参与计算的 token 数会放大约十倍。

> 实测：**110 秒 → 19 秒**（按文本长度排序后分批编码，batch=64，
> 同批内长度接近、padding 浪费最小）

**② 磁盘缓存 —— 按语料指纹失效**

缓存 key 由三者共同决定：

```
语料指纹（条目内容 SHA1） + 嵌入后端名 + 向量维度
```

语料改一个字、换个模型、换维度，指纹就变、缓存自动失效。
**不会出现新旧向量混用**——这是向量系统最隐蔽的一类 bug。

> 缓存命中：**16ms**

**③ 启动预热**

在 `serve_forever()` **之前**完成建索引与预热，
让**第一个用户请求不承担建库耗时**。否则首个访问者要等 20 秒，
体验上等同于"服务挂了"。

> `[hit]` 表示走缓存；首次运行会显示 `[built]` 并耗时约 20 秒，属正常。

### 阶段 5 · 三层验证

不是"能打开页面"就算跑通。分三层，**越往下越接近真实**：

| 层 | 手段 | 验证什么 |
|---|---|---|
| ① 单元 / 链路 | `python tools/smoke_test.py` | 4 轮咨询 → 意图 → 工具 → 回答 → B 端线索，全链路时序 |
| ② 质量 | `python tools/eval_retrieval.py` | 44 题标注集，Hit@1 / Hit@3 / MRR，三通道对比 |
| ③ 集成 | 直连 `/api/health` + `/api/chat` | 真实 HTTP 路径，**绕开 curl 的中文编码坑** |

> **为什么必须有第 ② 层**：端到端跑通只证明"没有异常"，
> 不证明"检索结果是对的"。我这次遇到的三个最有价值的 bug
> （同分并列、否定假阴性、padding 拖慢）**全都能通过冒烟测试**，
> 只有量化评测能暴露它们。

## 二、工作流的落地运用

### 2.1 四层架构 → 目录结构

```
接入层      app/web/           浏览器单页 · C 端入口 · B 端入口
服务层      app/server.py      /api/chat · /api/leads · /api/health
AI 能力层   app/engine/        llm · nlu · embed · vector_index
                               · rag · tools · lead · generator
数据层      app/data/          law_kb.json · cases.json
                               · models/ · index_cache/ · sessions/
```

### 2.2 C 端五步工作流

每一步产出一条 trace，前端实时渲染：

```
① 接收输入        → 会话累计字数
② 意图识别        → 案件类型 + 置信度 + 诉求 + 命中关键词
③ 工具调用 ─┬─ 工具一 法条检索    （每次必调）
           ├─ 工具二 案例匹配    （触发词命中才调）
           └─ 工具三 风险评估    （每次必调，B 端强制）
④ 生成回答        → MoMA 路由到哪个模型 · Prompt 字数 → 输出字数
⑤ 风险提示        → 免责声明 + 时效提示
```

> **工具触发条件是有意设计的差异**：法条检索与风险评估是刚需，每次必跑；
> 案例匹配成本高、且只在有明确争议焦点时才有价值，因此设了触发词，
> 避免无谓调用。这是"Function Calling 该在什么时候调"的工程判断，
> 不是技术限制。

### 2.3 MoMA 多模型路由

| 档位 | 模型 | 适用场景 | 延迟 SLA |
|---|---|---|---|
| `intent` | 千问-Turbo | 意图识别 / 实体抽取 / 高频简单问题 | 500ms |
| `dialogue` | GLM-4（GLM-5.2） | C 端日常咨询 / 结构化建议输出 | 3000ms |
| `reasoning` | DeepSeek-V3 | 复杂法律推理 / 长会话分析 / B 端意向报告 | 8000ms |

路由不是写死的，由**复杂度公式**决定，所以演示时能看到模型随对话推进自动升档：

```
复杂度 = 1 + (召回法条 ≥ 4 ? 1 : 0)
           + (存在强意向信号 ? 1 : 0)
           + (会话轮次 ≥ 3 ? 1 : 0)
```

### 2.4 RAG 混合检索（本次改造最大的一块）

```
查询 ─┬─ 稠密通道：BGE 向量 → 余弦相似度 Top-N ─┐
      └─ 词面通道：IDF 加权二元组 Top-N ────────┤
                                            ├─ RRF 融合 → Top-K
              案件类型（category）元数据先验 ──┘
```

两通道**确实互补**，不是凑数：

| 通道 | 擅长 | 例子 |
|---|---|---|
| 稠密（向量） | 同义改写、口语化表达 | 「没签合同」≈「未订立书面劳动合同」（余弦 0.71） |
| 词面（IDF） | 精确信号、专有名词 | 「不安抗辩权」「竞业限制」「二倍工资」 |

用 **RRF（Reciprocal Rank Fusion）** 按**名次**而非分数融合，
天然规避两路分数量纲不可比的问题，k 取标准值 60。

> **对外接口一个字没改**：`search_statutes()` / `search_cases()` 的入参与
> 返回字段名完全保持，因此 `tools.py`、`generator.py` 零改动。
> 这是当初"先定接口、再换实现"的价值兑现。

### 2.5 B 端线索工作流

会话 → **可解释因子加权评分**（不是黑箱）：

```
+44  出现委托 / 起诉等强意向信号（找律师、律师费）
+12  案件类型明确
+10  主动询问程序 / 时效
 +8  紧迫性表达 · 会话轮次加成 · 提供具体事实
 → 等级：高（≥65） / 中（≥40） / 低
```

评分明细逐条落盘可回溯，律所可调参。产出包含：
**意向评级 · 案件标签 · 诉求拆解 · 风险等级 · 跟进建议 · 报价参考**。

## 三、迭代闭环：度量 → 定位 → 修复 → 复测

这是本次最值得复用的部分——**不靠感觉调参，四步一个循环**。

| 循环 | 现象 | 定位手段 | 根因 | 修复 | 复测结果 |
|---|---|---|---|---|---|
| 1 | 融合后 Hit@1 反而**低于**纯向量 | RRF 权重扫描 | 词面通道质量太差，融合在拖后腿 | 转下一层定位 | — |
| 2 | 向量明明排第一，结果里却没它 | 打印两通道各自名次 | **30 条并列同分**，排序退化成按条号大小，把正确结果挤出 Top-4 | 词面改 **IDF 加权** | 词面 Hit@1 **36.4% → 47.7%** |
| 3 | 建库耗时 **110 秒** | 分段计时 | 一次性 padding 到最长条目 | 按长度排序后分批编码 | **110s → 19s**，缓存 16ms |
| 4 | 「能不能要二倍工资」漏判证据 | 构造 8 条否定用例 | 「能不能」的「不」被误判为否定 | 加非否定搭配白名单 | **8/8 通过**，且真否定仍生效 |
| 5 | 案例检索抛 `TypeError` | 冒烟测试 | `focus` 字段是**列表**不是字符串 | 拼接前展平 | 修复 + 补测试 |

### 循环 2 详解（最有代表性的一次）

**表面现象**：向量检索"不准"，正确法条召不回来。

**直觉反应**（错误）：模型太小 → 换个更大的模型。

**实际根因**：向量通道一直是**对的**——第八十二条余弦 0.700，全库第一。
真正的 bug 在词面通道：语料扩到 1037 条后 `keywords` 字段为空，
词面打分退化成"数公共二元组的个数"，
**一次查询出现 30 条并列同一分数**。Python 稳定排序只能按原文顺序排，
于是"Top-16"变成"条号最小的 16 条"。
这个毫无信息的列表混进 RRF 后，硬生生把正确的第八十二条挤出了结果。

**修复**：改为 **IDF 加权**。常见二元组（「劳动」「合同」）自动趋近零权重，
稀有二元组（「二倍」「竞业」）才起作用。同分并列消失，排序恢复信息量。

**结论**：如果直接换模型，会花掉大量时间与算力，而 bug 依然在。
**先定位再动手，比先动手省一个数量级的时间。**

### 最终指标（44 题标注集）

| 通道 | Hit@1 | Hit@3 | MRR |
|---|---|---|---|
| 词面通道（≈ 改造前水平） | 47.7% | 61.4% | 0.544 |
| 稠密通道（BGE 向量） | 47.7% | 68.2% | 0.580 |
| **混合融合（当前采用）** | **56.8%** | **68.2%** | **0.625** |

> 标注集规模有限（44 题），1~2 题的差异属噪声。
> 这张表说明的是**趋势**而非精确排名，明细会逐题打印未命中的问题。

## 四、一键复现命令

```bash
cd legalassist-demo

# ① 依赖与模型（可选：不装则自动降级为词面检索，服务照常可用）
pip install onnxruntime tokenizers
python tools/fetch_model.py

# ② 构建语料与索引（源文件缓存后，可完全离线重建）
python tools/build_corpus.py

# ③ 启动（首次约 20s 建索引，之后 16ms 走缓存）
python app/server.py --port 8000 --open

# ④ 三层验证
python tools/smoke_test.py        # 端到端链路
python tools/eval_retrieval.py    # 检索质量 + RRF 权重扫描
curl http://127.0.0.1:8000/api/health   # 运行态自检
```

**Windows 本机注意**：`python` 命令指向 Microsoft Store 占位程序会报错，
请直接双击 `启动Demo.bat`，或用完整路径
`"%LOCALAPPDATA%\Programs\Python\Python312\python.exe" app/server.py`。

## 五、沉淀下来的工程原则

1. **每一步都要留下可验证的证据。**
   条数对得上官方条数、语义分数区分得开、检索指标可复现——
   没有证据的"应该没问题"，在换个人接手时等于零。

2. **先定位，再动手。**
   循环 2 是最典型的例子：现象指向模型，根因在排序。
   定位的成本远低于试错。

3. **量化评测不可省。**
   冒烟测试只能证明"没报错"，不能证明"结果对"。
   本次三个最有价值的 bug 全部能通过冒烟测试。

4. **降级链要比优雅更重要。**
   `embed.py` 的 ONNX → API → hash 三级降级保证服务**永不因缺模型而挂**，
   同时用 `/api/health` 的 `semantic` 字段**如实暴露**当前能力级别——
   降级可以，但必须让人知道正在降级。

5. **缓存必须跟着内容走。**
   向量缓存的 key 包含语料指纹，语料一改自动失效。
   否则会出现"改了知识库但检索结果没变"这类极难排查的问题。

6. **接口先定，实现后换。**
   Phase 0 先按向量检索的形态定好 `search_statutes()` 的入参与返回字段，
   Phase 1 换实现时上层零改动。这个顺序反过来会付出数倍的代价。
