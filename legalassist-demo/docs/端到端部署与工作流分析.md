# 智能律询通 · 端到端部署与工作流分析

本文把 PPT 里的架构描述，逐条落成可运行的工程实现，并说明每一处的取舍。

## 一、端到端部署架构

### 1.1 四层架构的落地

PPT 第 9 页给出的四层架构，在 Demo 中直接映射为目录结构：

```

├─────────────────────────────────────────────────────────┤

│   /api/chat 智能对话引擎                                 │
│   /api/leads 意向客户分析引擎 · 律师工作台 API           │

├─────────────────────────────────────────────────────────┤

└─────────────────────────────────────────────────────────┘
```

### 1.2 部署形态

| 项目 | Demo | 生产 |
|---|---|---|
| 运行时 | Python 3 标准库 | Python 3.11+ / JVM |
| 依赖 | **0 个第三方包** | FastAPI, uvicorn, SQLAlchemy… |
| 并发 | `ThreadingHTTPServer` | Gunicorn/Uvicorn workers + Nginx |
| 存储 | JSON 文件 | PostgreSQL + Redis |
| 配置 | 环境变量 | 配置中心 + 密钥管理 |
| 可观测 | 调用日志 + 路由统计 | OpenTelemetry + Prometheus |

**为什么 Demo 坚持零依赖？**
评审/演示场合最怕"装不上跑不起来"。用标准库实现，`python app/server.py` 一条命令即可，
把工程复杂度留给真正需要的地方（AI 能力层），而不是环境搭建。

### 1.3 模型接入的两种模式

```
               ┌──────────────────────────────────┐
   Prompt ───► │  LLMClient.complete(task, ...)   │
               └──────────────┬───────────────────┘
                              │
                    LEGALASSIST_LLM = ?
                    ┌─────────┴─────────┐
              mock  │                   │  openai-compatible
                    ▼                   ▼
        ┌───────────────────┐   ┌────────────────────┐
        │ 本地规则引擎      │   │ 真实模型 HTTP 调用 │
        │ (离线可跑通)      │   │ 失败→自动降级回左边 │
        └───────────────────┘   └────────────────────┘
```

关键设计：**接口只有一个 `complete()`**。无论 mock 还是真实模型，
上层（pipeline / lead）完全无感。这让"演示"和"上线"共用同一套业务代码，
切换只改环境变量。

## 二、C 端工作流分析（五步流程）

PPT 第 6 页的 C 端五步流程，在 `engine/pipeline.py::handle_chat()` 中逐步实现，
每一步都产出一条 **trace 埋点**，前端右侧面板实时渲染。

```
用户输入 "公司没签劳动合同11个月了，还拖欠工资，我想找律师"
   │
   ├─ 1. 用户输入 ────────────────────────────────────────
   │     记录轮次、字数，取出多轮 history
   │
   ├─ 2. 意图识别            [MoMA → 千问-Turbo]  ← 延迟优先，<500ms
   │     nlu.recognize()
   │       · 分类：labor/marriage/contract/loan  (关键词加权)
   │       · 多轮先验：历史会话类型 × 0.3 权重
   │       · 诉求：主张金钱给付 / 解除关系 / 程序时效 / 证据 / 权利确认
   │       · 实体：金额(万元归一) / 时长 / 时间点 / 当事人
   │     输出：劳动纠纷 98% · 程序与时效咨询
   │
   ├─ 3. 工具调用（Function Calling 链）
   │     ├ 工具一 法条检索  [始终调用]  → Top-4 法条 + 相关度
   │     ├ 工具二 案例匹配  [条件触发]  → 命中"类似/怎么判/法院会"才调
   │     └ 工具三 风险评估  [始终调用]  → 证据覆盖率 + 风险等级 + 概率区间
   │
   ├─ 4. 生成回答            [MoMA → GLM-4 或 DeepSeek-V3]  ← 按复杂度路由
   │     generator.build_prompt() 动态注入检索上下文
   │     generator.render_answer() 强制三段式输出
   │
   └─ 5. 风险提示 ────────────────────────────────────────
         时效提示 + 逐条风险 + 免责声明
```

### 2.1 路由策略的实测表现

`llm.route()` 的判定依据（与 PPT 描述一致）：

| 档位 | 模型 | 触发条件 |
|---|---|---|
| intent | 千问-Turbo | 任务类型 = 意图识别 |
| dialogue | GLM-4 | 常规对话：复杂度 < 3 且 Prompt < 1200 字 |
| reasoning | DeepSeek-V3 | 复杂度 ≥ 3 或 Prompt ≥ 1200 字 或 B 端分析 |

复杂度公式（`generator.generate()`）：

```
complexity = 1 + (法条命中 ≥ 4 ? 1 : 0)      // 涉及多部法律法规
               + (有强意向信号 ? 1 : 0)      // 已表达委托/诉讼意向
               + (轮次 ≥ 3 ? 1 : 0)          // 长会话上下文
```

实测一次 4 轮对话（`tools/smoke_test.py` 的输出），路由自然分层：

```
                       法条  轮次先验  强意向   复杂度      路由
第 1 轮  没签劳动合同   4 条    -        -      1+1 = 2   GLM-4
第 2 轮  拖欠工资社保   4 条    -        -      1+1 = 2   GLM-4
第 3 轮  问仲裁时效     4 条    -        -      1+1 = 2   GLM-4
第 4 轮  想找律师起诉   4 条    +1       +1     1+3 = 4   DeepSeek-V3
```

（"轮次先验"按**进入本轮之前**的已完成轮数算，所以第 4 轮才满足 `轮次 ≥ 3`。）

这正是 PPT 想表达的"按场景最优匹配"：简单问题走廉价档位省钱，
复杂/长会话才上高成本模型。

### 2.2 Prompt 工程四大策略的实现

| PPT 策略 | 实现 | 代码位置 |
|---|---|---|
| ① 系统角色设定 | `SYSTEM_ROLE` 定义资深法律顾问人设 + 回答边界 + 不得承诺结果 | `generator.py` |
| ② RAG 上下文动态注入 | 检索结果按 `relevance` 降序拼入 Prompt，标注来源条款与相关度 | `generator.build_prompt()` |
| ③ 输出格式结构化约束 | 强制「法律依据 → 证据清单 → 维权路径」三段式 + 末尾风险提示 | `generator.render_answer()` |
| ④ 多轮记忆管理 | 超 10 轮压缩为摘要 + `key_facts` 关键事实沉淀 | `generator.compress_history()` |

### 2.3 三个工具的触发条件（对照 PPT）

```python
工具一 tool_search_statutes   # 触发：提问涉及具体法律问题（默认调用）
工具二 tool_match_cases       # 触发：命中 类似/怎么判/先例/案例/能赢吗/胜诉
                              #       或轮次 ≥ 2（已进入深聊）
工具三 tool_assess_risk       # 触发：始终调用（PPT：B 端分析必调）
```

### 2.4 两个容易被忽略的工程细节

**(1) 否定感知匹配** — 这是法律场景的刚需。

用户说「公司**没**跟我签劳动合同」，字面包含「劳动合同」四个字。
朴素关键词匹配会得出"用户已具备书面劳动合同"的荒谬结论，
并把它算进证据覆盖率。`textutil.keyword_present()` 检查关键词前 8 个字符
是否含否定标记（没/未/无/不/缺/丢…），命中则判定该事实**不存在**。

**(2) 主张事实抽取** — 用户陈述的是"事实"，不是"证据"。

用户很少说"我有工资流水"，而是说"公司拖欠我工资"。
`tools.extract_claims()` 把「否定/受损表述 + 对象词」识别为**待证明的事实主张**：

```
"没跟我签劳动合同"  → 未签订书面劳动合同
"拖欠上个月的工资"  → 被拖欠劳动报酬
"社保也没交"        → 未依法缴纳社会保险
```

这才是律师打开线索时最想看的东西——**当事人主张什么**。
同时它跨轮累积，第 3 轮时会话已经沉淀出完整的事实主张清单。

## 三、B 端工作流分析（意向客户分析）

PPT 第 6 页的 B 端流程，实现在 `engine/lead.py`。

```
输入：完整咨询会话（含多轮上下文 + 累积的意图与实体）
   │
   ├─ 信号汇总  lead._collect()
   │     抽取：强意向词 / 紧迫词 / 诉求类型 / 最大涉案金额 / 轮次
   │
   ├─ 意向评分  lead.score()   ← 可解释因子加权，非黑箱
   │     ┌─────────────────────────────────────┬──────┐
   │     │ 出现委托/起诉等强意向信号            │ +22/个│ (上限45)
   │     │ 会话轮次 ≥ 3                         │  +8  │
   │     │ 会话轮次 ≥ 6                         │ +10  │
   │     │ 案件类型明确（非"其他"）             │ +12  │
   │     │ 涉案金额 ≥ 1 万                      │ +10  │
   │     │ 涉案金额 ≥ 10 万                     │  +8  │
   │     │ 主动询问程序/时效                    │ +10  │
   │     │ 主动询问证据                         │  +8  │
   │     │ 存在紧迫性表达                       │  +8  │
   │     │ 提供了金额/时长等具体事实            │  +8  │
   │     └─────────────────────────────────────┴──────┘
   │     总分 0-100 →  高 ≥65 ｜ 中 ≥40 ｜ 低
   │
   ├─ 证据与风险  复用工具三（PPT：B 端分析必调）
   │
   ├─ 跟踪建议生成（面向律师的可执行动作）
   │     优先跟进建议 + 补齐证据清单 + 风险沟通话术 + 抗辩预判 + 报价参考
   │
   └─ 经 DeepSeek-V3 生成完整分析报告文本
```

### 3.1 为什么用"可解释因子"而不是黑箱模型

PPT 提到"意向评分模型"。Demo 用**加权规则**而非机器学习模型，理由是：

- 律所对案源评级有强解释诉求——"为什么这条是高风险线索"必须能答上来；
- 冷启动阶段没有标注数据，规则可先跑起来；
- 权重表 `WEIGHTS` 独立可配，律所可按自身业务调整（比如婚姻家事权重更高）。

界面上「意向评分明细」把每一项加分和理由都列出来，评委可以直接看到推理过程。

升级路径：积累真实转化数据后，用这些因子作为特征训练 LR/GBDT，
规则分作为 baseline 对比。

### 3.2 完整链路串联

```
C 端会话 ──► store.save() ──► app/data/sessions/*.json
                                      │
                                      │  lead_cache 失效（history 长度变化）
                                      ▼
                              pipeline.get_lead()
                                      │
                                      ▼
                           B 端线索池 /api/leads
                                      │
                                按案件类型、意向等级、跟进状态筛选
                                      │
                                      ▼
                              律师标记「待跟进/已联系/已转化」
```

同一份会话数据，C 端看到的是"法律建议"，B 端看到的是"案源线索"——
这就是 PPT 说的 **数据闭环：C 端咨询会话 → AI 结构化分析 → B 端律师线索池 → 转化为委托案件**。

## 四、效果评估的埋点基础

PPT 第 12 页列出的评估指标，在 Demo 中已有对应的数据采集点：

| PPT 指标 | Demo 采集位置 |
|---|---|
| 平均响应时长（P95） | `llm.call_log[].latency_ms`，含 SLA 达标标记 |
| 法条引用正确率 | `references.statutes[].relevance` 可人工核验 |
| 模型路由分布 | `/api/router/stats` 按模型聚合调用数与均耗时 |
| 意向评级准确度 | `lead.score_detail` 完整留痕，可回溯 |
| 幻觉率 | 回答中的法条**只能来自知识库检索结果**，结构上杜绝编造条号 |

最后一条是这个架构的隐含优势：因为强制「先检索、再生成」，
模型没有机会凭空引用一条不存在的法条——引用来源被约束在检索结果内。

## 五、检索层升级记录（Phase 1）

最初的检索层是「关键词词表命中 + 字符二元组重合」——本质是词面匹配，
问法换个说法就召回不到。Phase 1 换成了真正的混合向量检索。

### 5.1 改造范围

| 组件 | 文件 | 作用 |
|---|---|---|
| 嵌入层 | `engine/embed.py` | BGE-small-zh-v1.5 ONNX（512 维），ONNX → API → hash 三级降级 |
| 向量索引 | `engine/vector_index.py` | numpy 余弦检索 + 磁盘缓存（按「语料指纹+后端+维度」失效） |
| 混合检索 | `engine/rag.py` | 稠密 + 词面双通道，RRF 融合（k=60） |
| 语料构建 | `tools/build_corpus.py` | 从公开法律仓库解析 1037 条法条，补时效元数据 |
| 检索评测 | `tools/eval_retrieval.py` | 44 题标注集，三通道对比 + RRF 权重扫描 |

关键约束：**对外接口保持不变**。`search_statutes()` / `search_cases()` 的入参与
返回字段名一个没改，所以 `tools.py` 与 `generator.py` 零改动。

### 5.2 实测结果

44 题标注集（口语化提问 32 + 规范术语 12）：

| 通道 | Hit@1 | Hit@3 | MRR |
|---|---|---|---|
| 词面通道（≈ 改造前水平） | 47.7% | 61.4% | 0.544 |
| 稠密通道（BGE 向量） | 47.7% | 68.2% | 0.580 |
| **混合融合（当前采用）** | **56.8%** | **68.2%** | **0.625** |

两条通道确实互补：口语化提问上稠密通道更强（「没签合同」vs「未订立书面劳动合同」
余弦 0.71），规范术语提问上词面通道更强（「不安抗辩权」「竞业限制」这类专有名词
向量容易糊掉）。融合后 Hit@1 比任一单通道高约 9pp。

### 5.3 过程中修掉的三个真问题

这一节记录的是**踩坑本身**，因为它们的成因比结论更有参考价值。

1. **词面通道同分并列，排序退化成按条号大小**。
   改造后语料扩到 1037 条，但 `keywords` 字段是空的，词面打分退化为"数公共二元组
   个数"。一次查询出现 **30 条并列同一分数**，Python 稳定排序只能按原文顺序排，
   于是"Top-16"变成"条号最小的 16 条"。这个毫无信息的列表混进 RRF 后，把向量
   通道找对的第八十二条（余弦 0.700，全库第一）挤出了 Top-4。
   → 改为 **IDF 加权**：常见二元组（「劳动」「合同」）自动趋近零权重，
   稀有二元组（「二倍」「竞业」）才起作用。同分并列消失，词面通道 Hit@1 从
   36.4% 升到 47.7%。

2. **建库耗时 110 秒**。885 条法条一次性 padding 到最长条目（392 字），
   实际参与计算的 token 数放大约十倍。
   → 按文本长度**排序后分批编码**（batch=64），同批内长度接近、padding 浪费最小，
   建库降到约 19 秒，此后走磁盘缓存 26ms。

3. **否定匹配的假阴性**。「能不能要二倍工资」里的「不」属于「能不能」，
   不表否定，但启发式规则一律当否定处理，导致二倍工资这个关键证据被漏判。
   → 加入非否定搭配白名单（能不能 / 是否 / 不仅 …），同时保留
   「公司没跟我签劳动合同」这类**真否定**的识别（已加回归用例）。

### 5.4 仍然做不到的

1. **合同编内部辨析难**。民法典合同编 576 条语义高度接近，「一物二卖」会被
   597 / 643 / 629 多条同时命中，Top-1 不稳定。需要 Cross-Encoder 精排。
2. **跨法版本冲突不会自动裁决**。劳动法第 82 条（旧的 60 日仲裁期限）已被
   劳动争议调解仲裁法第 27 条（1 年）取代，两条都与提问相关，系统会同时召回，
   但不会判定新法优于旧法。时效元数据已标注，裁决逻辑尚未实现。
3. **复合提问被稀释**。「要花钱吗 + 多久内必须申请」这类多问题句，向量相似度被
   摊平，单条法条排名下滑。需要查询分解（query decomposition）。
4. **短查询向量区分度低**。仅「双倍工资」四字时全库余弦挤在 0.43~0.48，
   靠词面通道才能拉开——这是 24M 小模型的固有局限。

## 六、已知局限（诚实说明）

1. **案例库是虚构演示数据**，不可作为法律依据。
2. **胜诉概率区间是启发式估算**，不是真实统计模型，仅供演示评分机制。
3. **无用户鉴权、无并发压测**，不适合直接对外提供服务。
4. **Chinese-only**：分词与关键词表都基于中文法律语料。
5. **检索标注集只有 44 题**，1~2 题的差异属噪声，结论是趋势而非精确排名。

---

## 七、下一步建议

按投入产出比排序：

1. **换更强的嵌入模型**：`bge-small-zh`(24M) → `bge-large-zh`(326M) 或 `bge-m3`，
   预期短查询区分度明显改善。接口不变，改 `config.EMBED_MODEL_DIR` 即可。
2. **加 Cross-Encoder 精排**：在 RRF 召回后对 Top-20 做精排，这是解决"合同编内部
   辨析难"最直接的手段。
3. **法条时效自动裁决**：基于已标注的 `status` / `effective_date`，实现
   "新法优于旧法、特别法优于一般法"的冲突消解。
4. **扩评测集**：从 44 题扩到 300+，覆盖四个案件类型，接入 RAGAS 自动评测。
5. **接入真实模型**：配置 `LEGALASSIST_LLM=openai-compatible`，对比 mock 与真实输出差异。
